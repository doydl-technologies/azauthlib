5. Credentials, browser sign-in, and device codes

Tenant IDs and client IDs are stored as configuration values; client secrets entered for storage are submitted to the configured operating-system credential backend. Secrets may be shared by profiles that use the same client ID. Review backend settings on shared, managed, or non-Windows devices; the App does not create an isolated hardware security boundary around every stored value.

Interactive sign-in normally opens a browser and may use a local loopback redirect. Device-code sign-in shows a short-lived code and verification address. Enter codes only at the intended Microsoft sign-in destination and only when you initiated the operation. Never accept a code from an untrusted person claiming to provide support.

Microsoft may request a password, multifactor authentication, conditional-access checks, account selection, or consent. Those interactions are governed by Microsoft and your organization. The App's own form is not intended to collect your Microsoft account password.

Do not disclose client secrets, access or refresh tokens, device codes, private keys, browser session data, or unredacted configuration files in support requests, public issues, recordings, or screenshots. If a credential is exposed, stop affected activity and rotate or revoke it through the issuing service. Removing a profile does not perform that revocation.

7. Local data, backups, and removal

Profiles, public configuration, display preferences, and saved test outcomes are maintained in application data on your device. The current removal workflow removes the active registry entry and associated saved outcome, recoverably archives known configuration/cache files in removed-profiles, and keeps OS-stored secrets because another profile may share them. Files not known to that workflow and copies outside application storage may remain.

Uninstalling the App is not represented as deleting all application data, archives, browser sessions, keyring entries, or backup copies. 8. Security responsibilities

Protect the operating-system account that runs the App. Use appropriate disk encryption, current security updates, trusted software sources, least-privilege access, and organizational endpoint controls. Do not assume encryption at rest prevents access by an unlocked session, malware, an administrator, or a compromised dependency.

The desktop test uses a temporary in-memory token cache. The separate Python library may persist tokens, normally using operating-system-backed encryption; explicit plaintext-cache configuration is possible for library callers. Review the mode actually used by your integration rather than relying on a single statement about all azauthlib deployments.

No software or security measure is infallible. Authentication errors, expired secrets, policy changes, network interception by a managed proxy, operating-system behavior, and dependency vulnerabilities can affect operation. A successful test is not evidence that a system is free from security defects.

Report a suspected vulnerability using the repository's private vulnerability reporting channel described in SECURITY.md. Do not post live credentials or sensitive exploit details in a public issue. Where a report involves an active compromise, also notify the relevant tenant or system administrator.
